# 앱 내 업데이트와 GitHub 릴리스

Windows 설치 버전의 **설정 → 앱 업데이트**에서 **업데이트 확인 → 업데이트 다운로드 → 재시작하여 적용**을 사용한다. GitHub의 `winter3671/maple-roster` 공개 Releases에서 정식 최신 버전을 확인하며, 다운로드 진행률을 표시한다. 앱 실행 시 자동으로 조회하거나 다운로드하지 않고, 다운로드 완료 후에도 평소 앱 종료만으로 설치하지 않는다. 이전 버전과 사전 배포 버전은 받지 않는다.

재시작 적용 전에 작성 중인 입력을 저장한다. 확인 버튼을 누르면 진행 중인 다른 API·장부 요청이 없는지 확인하고 JSON 자동 백업을 강제로 저장한 뒤 설치·재시작한다. 백업 실패나 다른 작업 진행 중에는 적용하지 않고 다운로드 상태를 유지하므로 문제를 해결하고 다시 시도할 수 있다. 장부와 API 키의 기존 저장 위치는 유지한다. 앱이 다운로드 중 종료되었다면 다시 확인·다운로드하며, 유효한 캐시 파일은 업데이터가 재사용할 수 있다.

개발 실행(`npm run dev`)에서는 업데이트 버튼을 비활성화한다. 설치 파일에 포함된 `app-update.yml`을 메인 프로세스의 `electron-updater`가 읽고, 화면에서 임의의 URL이나 실행 파일 경로를 넘기지 않는다. 다운로드 파일의 해시 검증은 업데이터가 수행한다. 현재 개인용 Windows 빌드는 무서명이므로 코드 서명으로 게시자를 인증하는 구성은 추후 배포 단계에서 추가한다.

## 처음 사용하는 경우

기존 v0.1.0에는 업데이트 기능이 없으므로 v0.2.0 설치 파일로 한 번 재설치한다.

```bash
npm run dist:win
```

생성 파일: `release/Maple-Roster-Setup-0.2.0-x64.exe`. 이번 작업에서 생성한 파일을 바로 설치할 수 있다. 이후 버전은 Releases에 정상 게시되면 앱 안에서 업데이트한다. 릴리스나 필수 파일이 없거나 인터넷 연결이 안 되면 오류를 안내하며, 이를 최신 버전이라는 결과로 표시하지 않는다.

## 새 버전을 게시하는 방법

**설정 → 업데이트 내역**에는 앱에 포함된 릴리스 노트가 표시된다. 다음 버전을 배포할 때 `src/shared/release-notes.json`에 해당 버전·배포 날짜·사용자용 변경 사항을 먼저 추가한다. 앱과 GitHub Releases는 같은 파일을 사용하며, 노트가 없거나 형식이 잘못되면 배포를 중단한다. 작성 방법과 브랜치 운영은 [릴리스 노트](release-notes.md)를 참고한다.

앱 안의 업데이트 확인은 개발 코드나 Git 커밋을 직접 받는 기능이 아니다. 새로운 버전 번호와 설치 파일을 Releases에 게시해야 한다. `.github/workflows/release.yml`은 `v*` 태그가 원격 저장소에 올라오면 Windows에서 의존성 설치·테스트·타입 검사·빌드·패키징을 수행한다. 태그가 `package.json` 버전과 다르거나 사전 배포 번호이면 중단한다.

최초 v0.2.0은 변경 사항을 커밋하고 푸시한 뒤 다음을 실행한다.

```bash
git tag v0.2.0
git push origin v0.2.0
```

다음 기능 배포 예시는 다음과 같다. 버전을 올리고 해당 버전의 노트를 작성한 뒤 미리 보기 검사를 실행한다. 이미 게시한 버전 번호와 태그는 재사용하지 않는다.

```bash
npm version patch --no-git-tag-version
# src/shared/release-notes.json에 v0.2.2 내역을 먼저 작성
npm run release:notes
git add .
git commit -m "chore: 앱 패치 버전 갱신"
git push
git tag v0.2.2
git push origin v0.2.2
```

GitHub의 **Actions → Windows release**에서 성공을 확인하고 **Releases**에서 공개 정식 릴리스를 확인한다. 워크플로는 설치 EXE·EXE의 blockmap·`latest.yml`을 먼저 드래프트 릴리스에 모두 올린 뒤 공개한다. 업로드 실패 시 드래프트 상태에 남고, 공개 단계 실패 시 오류로 끝나므로 파일을 확인한 뒤 복구한다. 같은 태그의 기존 릴리스가 있으면 임의로 덮어쓰지 않는다. `GH_TOKEN`은 작업에 제공되는 GitHub 토큰만 사용하며 개인 토큰이나 넥슨 API 키를 앱에 넣지 않는다.

처음에는 실제 GitHub Actions 실행과 다음 버전의 설치·재시작 확인이 필요하다. 로컬 검증에서는 테스트 서버로 메타데이터 조회·실제 설치 파일 다운로드·해시 검증·적용 확인·자동 백업을 확인했고, 실제 설치 실행은 테스트에서 가로채어 기존 설치와 장부를 보호했다.

기준 문서: [electron-builder v26 Auto Update](https://www.electron.build/v26/docs/features/auto-update/).

## 개발 실행과 설치 앱의 저장소

설치 앱은 기존 `%APPDATA%/maple-roster`를 계속 사용한다. 개발 실행은 `%APPDATA%/maple-roster-dev`를 사용하여 개발 중 DB 변경이 설치 앱의 실행에 영향을 주지 않게 한다. `MAPLE_ROSTER_DATA_DIR`를 지정하면 테스트용 경로가 우선한다. 기존 장부는 설치 앱 폴더에 그대로 남는다. 개발용 장부가 없거나 비어 있으면 최초 실행 시 기존 설치용 DB의 일관성 백업을 복사하여 기록을 이어서 볼 수 있다. 이미 개발 기록이 있으면 덮어쓰지 않고, 초기 복사가 끝난 뒤에는 다시 복사하지 않는다. 원본 DB는 수정하지 않으며 테스트용 경로와 설치 실행에는 이 복사를 적용하지 않는다. 이후 두 장부는 독립적으로 저장되므로 개발 기록을 설치 앱으로 옮길 때는 JSON 백업·복원을 사용한다.

앱 버전이 최신이 아니라는 이유만으로 실행을 막지 않는다. 다만 장부가 해당 앱보다 새로운 DB 구조라면 오래된 코드로 수정하지 않고 업데이트 전용 화면을 연다. 여기서 업데이트 확인·다운로드·재시작 적용을 수행할 수 있다. 적용 전에 원본 DB를 읽기 전용으로 열고 SQLite 백업을 `backups/recovery`에 저장하여 알 수 없는 DB 구조와 WAL의 최신 기록을 함께 보존한다. 일반 장부 실행의 JSON 자동 백업은 기존 방식을 유지한다.

이 복구 기능이 없는 기존 설치 앱이 이미 최신 개발 DB를 공유했다면 새 설치파일로 한 번 교체해야 한다. 소스 코드 변경이나 커밋만으로 설치된 실행파일이 변경되지는 않는다. 이후 업데이트는 더 높은 버전의 정식 GitHub Release가 게시되었을 때 앱에서 받을 수 있다.
