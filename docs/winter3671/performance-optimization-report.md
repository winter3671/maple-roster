## 3. 자동 백업 반복 확인

### 변경 내용

이전에는 장부가 바뀌지 않아도 전체 장부를 내보내고 기존 자동 백업 파일들을 읽어 내용을 비교했다. 개선 후에는 SQLite의 `total_changes`와 `data_version`으로 DB 변경을 확인하고, 파일 식별자·크기·나노초 수정/변경 시각으로 백업 검증 결과를 재사용한다. 같은 프로세스에서 DB와 최신 백업이 그대로이면 전체 내보내기를 생략한다.

최초 확인·앱 재실행·실제 DB 변경·강제 백업은 전체 내보내기와 검증을 수행한다. 백업 파일이 삭제되거나 바뀌면 다시 확인하며, 업데이트 전 강제 백업과 정상 자동 백업 최근 30개 보관 정책은 유지한다.

## 4. 주간·월간 보스 API 요청 통합

### 변경 내용

주간·월간 보스 기록을 한 IPC 요청으로 확인하고, 같은 캐릭터 OCID·실제 조회일·기준일의 스케줄러 응답을 그 요청 안에서 재사용한다. 조회 날짜가 다르면 각각 요청하며 재확인 버튼을 누르면 새 API 응답을 받는다. 실패 응답도 동일 요청 안에서 재사용하여 불필요한 재요청을 막는다.

### 검증된 요청 수

| 조건                                     | 이전 | 이후 | 감소율 |
| ---------------------------------------- | ---: | ---: | -----: |
| 캐릭터 2명, 주간·월간의 실제 조회일 동일 |  4회 |  2회 | 50.00% |
| 같은 조건의 캐릭터 N명                   | 2N회 |  N회 | 50.00% |

2명 조건은 가짜 전송 함수의 호출 횟수로 검증했다. N명 조건은 동일한 재사용 규칙을 일반화한 값이다. 실제 API 네트워크 지연이나 조회 완료 시간은 측정하지 않았으므로 시간 개선율은 제시하지 않는다. 주간·월간 검증·저장은 독립적으로 처리하여 한쪽 응답만 잘못되어도 다른 쪽 성공 기록을 유지한다.

검증 명령: `npm test -- src/backend/tests/boss-sync.integration.test.ts`

관련 구현: [boss-sync.service.ts](../../src/backend/modules/bosses/boss-sync.service.ts) · 검증 코드: [boss-sync.integration.test.ts](../../src/backend/tests/boss-sync.integration.test.ts)

## 5. 페이지 코드 지연 로딩

### 변경 내용

대시보드는 초기 코드에 포함하고 다른 6개 페이지는 해당 메뉴를 처음 열 때 `React.lazy`로 불러온다. 보스 장부의 주간·월간 기록 화면과 업데이트 전용 복구 화면도 별도로 분리했다. 화면 준비 안내와 로딩 실패 시 메뉴 이동은 유지한다.

### 초기 코드량

| 지표                      |            이전 |          이후 |           차이 | 감소율 |
| ------------------------- | --------------: | ------------: | -------------: | -----: |
| 초기 진입 JavaScript 합계 | 1,020,390 bytes | 695,569 bytes | −324,821 bytes | 31.83% |

지연 로딩 적용 당시 전체 JavaScript 합계는 **1,030,608 bytes**였다. 코드 분리와 오류 안내로 전체 코드량은 소폭 늘었지만 초기 화면에서 필요한 코드량을 줄였다. 이 값은 `90b54d7` 단계의 빌드 결과이며 이후 거래 페이지 변경을 포함한 최신 전체 크기와 구분한다.

Vite 빌드 매니페스트에서 초기 진입 파일과 정적 의존 파일만 합산했다. 동적 import 파일은 초기 크기에서 제외한다. 압축 전 파일 크기이며 CSS·이미지·Electron 런타임은 포함하지 않는다. 따라서 설치파일 크기나 앱 실행 시간이 31.83% 줄었다고 해석할 수 없다.

Electron 임시 DB에서 CDP의 `Debugger.scriptParsed` 이벤트로 초기 대시보드에 다른 페이지 코드가 포함되지 않는지, 메뉴·보스 내부 화면·업데이트 복구 진입 시 필요한 코드가 실행되는지 확인했다. 실제 시작 시간은 별도로 측정하지 않았다.

재현 명령:

```bash
npm run build
npm run perf:bundle
```

## 6. 대시보드 대량 장부 조회

### 변경 내용

이전 경로는 기간 내 거래 전체의 상세 객체와 메모·통화·분류 정보를 배열로 읽은 후 집계했다. 개선 경로는 집계에 필요한 **8개 필드**를 SQLite iterator로 한 건씩 처리한다. 최근 거래는 DB에서 먼저 **5건**을 선택한 후 그 거래의 상세 정보만 연결한다.

수입·지출·순수익, 사냥 드랍의 사냥 수입 합산, 캐릭터 순위와 이전 서버 표시 순서, 일별·월별 빈 구간, 최근 거래 정렬 기준을 유지한다. 금액은 BigInt로 정확히 합산하고 안전한 정수 범위 초과를 거부한다.

### 조회 시간

| 거래 수 | 전체 상세 경로 중앙값 | 개선 경로 중앙값 | 감소율 | 시간 비교 배수 | 전체 상세 경로 p95 | 개선 경로 p95 |
| ------- | --------------------: | ---------------: | -----: | -------------: | -----------------: | ------------: |
| 1,000   |               5.72 ms |          3.42 ms | 40.21% |         1.67배 |            6.94 ms |       4.38 ms |
| 10,000  |              95.02 ms |         30.70 ms | 67.69% |         3.10배 |           99.71 ms |      35.38 ms |
| 100,000 |           1,419.04 ms |        628.02 ms | 55.74% |         2.26배 |        1,462.53 ms |     660.54 ms |

10만 건의 중앙값은 **791.02 ms 감소**했고, p95는 **54.84% 감소**했다.

| 거래 수 | 상세 객체 생성 이전 | 상세 객체 생성 이후 |
| ------- | ------------------: | ------------------: |
| 1,000   |             1,000건 |                 5건 |
| 10,000  |            10,000건 |                 5건 |
| 100,000 |           100,000건 |                 5건 |

이는 메모 등 전체 상세 정보의 생성 건수다. 집계용 행은 여전히 기간 내 모든 거래를 순회하며 SQLite 정렬도 남아 있다. 메모리 사용량 감소율은 측정하지 않았다.

임시 파일 기반 SQLite에 캐릭터 6명과 관계가 유효한 사냥·수동 수입·수동 지출을 생성했다. 외래 키 검사와 집계 결과 일치를 확인하고, 두 경로를 예열한 뒤 실행 순서를 번갈아 각각 10회 측정했다. 비교 경로는 전체 상세 목록과 요약을 만들고 같은 집계 함수를 적용하는 방식이다. 데이터 생성·검증·IPC·화면 렌더링 시간은 측정에 포함하지 않는다.

재현 명령: `npm run perf:ledger`

## 7. 거래 목록 페이지 조회와 집계 재사용

### 변경 내용

상세 내역은 지출과 직접 수익을 DB에서 필터링한 후 **50건씩** 선택한다. 선택한 거래에 대해서만 메모·분류·통화 정보를 연결하고 화면에 전달한다. 페이지를 바꿔도 상단 합계·보스·사냥·직접 수익 요약은 기간 전체 기준이다. CSV와 백업도 전체 원본 거래를 유지한다.

집계에 필요한 필드만 순회하고 **마지막 조회 조건의 작은 집계 결과 1개**만 보관한다. 같은 연결의 `total_changes` 또는 다른 연결의 `data_version`이 바뀌거나 필터가 달라지면 다시 집계한다. 거래 상세 정보는 캐시하지 않고 매번 새로 읽는다.

### 중앙값과 감소율

| 거래 수 |   전체 조회 | 첫 페이지 | 첫 페이지 감소율 | 후속 페이지 | 후속 페이지 감소율 | 후속 페이지 시간 비교 배수 |
| ------- | ----------: | --------: | ---------------: | ----------: | -----------------: | -------------------------: |
| 1,000   |     5.46 ms |   1.57 ms |           71.25% |     0.48 ms |             91.21% |                    11.38배 |
| 10,000  |    82.48 ms |  13.13 ms |           84.08% |     0.83 ms |             98.99% |                    99.37배 |
| 100,000 | 1,633.71 ms | 596.55 ms |           63.48% |    21.95 ms |             98.66% |                    74.43배 |

첫 페이지는 전체 집계를 다시 계산한 경우이고, 후속 페이지는 DB·필터 변경 없이 집계를 재사용한 **두 번째 페이지**다. 두 감소율 모두 전체 상세 조회 시간을 기준으로 계산했다. 후속 페이지 21.95 ms는 마지막 페이지나 모든 페이지의 평균을 뜻하지 않는다.

### p95

| 거래 수 | 전체 조회 p95 | 첫 페이지 p95 | 후속 페이지 p95 |
| ------- | ------------: | ------------: | --------------: |
| 1,000   |       6.02 ms |       1.86 ms |         0.50 ms |
| 10,000  |      90.96 ms |      17.34 ms |         1.13 ms |
| 100,000 |   1,671.33 ms |     649.99 ms |        22.53 ms |

### 응답 크기

| 거래 수 |    전체 목록 응답 |  페이지 응답 | 감소율 |
| ------- | ----------------: | -----------: | -----: |
| 1,000   |   1,087,765 bytes | 71,434 bytes | 93.43% |
| 10,000  |  10,882,769 bytes | 71,444 bytes | 99.34% |
| 100,000 | 108,832,773 bytes | 71,454 bytes | 99.93% |

응답 크기는 전체 목록 또는 페이지 결과를 JSON으로 직렬화한 UTF-8 byte 수다. 실제 IPC 전송 바이트를 계측한 값은 아니다. 가짜 수동 거래에 긴 한글 메모를 넣었으므로 일반적인 사용자 응답 크기의 평균을 뜻하지 않는다. 다만 페이지 응답은 기간 전체 집계와 상세 50건으로 제한되는 것을 확인했다.

대시보드와 같은 가짜 장부를 사용하고 전체 조회·첫 페이지·후속 페이지를 예열된 SQLite에서 각각 10회 측정했다. 전체 조회에는 수익 묶음 계산도 포함한다. 첫 페이지는 매회 새 서비스를 만들어 집계 캐시를 사용하지 않도록 했다. 데이터 생성·검증·JSON 직렬화·IPC·React 렌더링 시간은 조회 시간에서 제외했다.

재현 명령: `npm run perf:ledger:pages`

## 8. 측정 환경과 검증 범위

| 항목                              | 기록                                                                                     |
| --------------------------------- | ---------------------------------------------------------------------------------------- |
| 측정 날짜                         | 2026-10-11                                                                               |
| 실행 환경                         | 같은 Windows 개발 기기에서 로컬 실행                                                     |
| 문서 작성 시 확인한 Node.js / npm | v24.19.0 / 11.17.0                                                                       |
| CPU·RAM·디스크 모델               | 기존 측정 기록에 상세 사양 없음                                                          |
| 사용자 데이터·실제 API 키         | 사용하지 않음                                                                            |
| 시간 측정                         | `performance.now()` 기반 ms                                                              |

| 통계                              | 중앙값과 nearest-rank p95. 10회 실험의 p95는 최댓값이므로 꼬리 지연 추정에는 표본이 적음 |
| 마지막 기능 작업 종료 시 테스트   | 425개 통과, 성능 실험 3개는 일반 실행에서 건너뜀                                         |

수치 표는 단계별 기록을 보존한 것이다. 각 비교는 자신의 동일 조건 안에서 해석해야 하며, 두 조회 실험의 전체 조회 시간이 다른 것은 별도 실행·측정 경로에 따른 차이다. 이전 배포 앱과 현재 설치 앱의 전체 체감 속도를 직접 비교한 결과는 아니다. 원시 stdout 로그는 별도 파일로 보관하지 않았으며, 현재 저장된 성능 문서와 재현 코드에서 측정 근거를 추적할 수 있다.

자동 테스트로 기존 합계·정수 계산·날짜/캐릭터 필터·CSV 범위·페이지 정렬·삭제 후 이동·캐시 무효화를 확인했다. Electron 임시 장부에서도 지연 로딩과 복구 진입, 거래 페이지 이동·합계 유지·수정·삭제·추가·빈 목록을 확인했다. 절대 시간으로 테스트의 통과 여부를 판정하지 않는다.

## 9. 아직 계측하지 않은 항목

| 항목                        | 현재 상태                    | 다음 측정 기준                                           |
| --------------------------- | ---------------------------- | -------------------------------------------------------- |
| 설치 앱 시작 시간           | 미측정                       | 실행 요청 → 창 표시 → 대시보드 준비, 최초/반복 실행 구분 |
| 앱 전체 메모리              | 미측정                       | 메인·렌더러·GPU 전체, 반복 화면 전환 후 회수 여부        |
| 실제 API 조회 지연          | 미측정                       | 네트워크 시간과 로컬 저장 시간 분리                      |
| 최초 백업·복원·변경 시 백업 | 이번 반복 확인 실험에 미포함 | 관계가 유효한 장부 크기별 확인                           |
| 뒤쪽 거래 페이지            | 두 번째 페이지만 시간 측정   | OFFSET 크기별 조회와 필요한 인덱스·커서 방식 검토        |
| IPC·화면 렌더링 시간        | 조회 시간에서 제외           | 응답 수신 → 표 표시 완료를 별도 측정                     |

10만 건의 최초 집계에는 개선 후에도 약 0.6초의 동기 처리가 남아 있다. 실제 설치 환경에서 메인 프로세스 반응성을 측정하고 필요하면 작업 스레드 분리를 진행한다. 초기 코드량·호출 횟수·상세 응답량 감소와 실제 사용자 체감 시간은 별도 지표로 계속 기록한다.

## 10. 이후 기록 방식

후속 최적화는 날짜·커밋·데이터 조건·반복 횟수·비교 경로·중앙값·p95·개선율을 함께 기록한다. 당시 결과는 덮어쓰지 않고 새 측정 행을 추가한다. 시간이나 메모리를 측정하지 않은 개선은 코드량·호출 수 등 실제 확인한 지표만 제시한다. 다음 측정부터는 실행 환경 사양과 벤치마크 stdout도 별도 파일로 남겨 비교 근거를 보강한다.
