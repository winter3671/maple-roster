# 성능 측정과 개선

측정은 설치 앱의 사용자 체감과 처리 비용을 구분한다. 합성 데이터 실험 결과를 실제 앱 시작 시간이나 전체 메모리 개선으로 해석하지 않는다. 실제 API 키·사용자 DB를 벤치마크에 사용하지 않는다.

## 자동 백업 확인 비용

실행: npm run perf:backup

임시 폴더에서 1천·1만 개의 합성 행을 포함하는 JSON과 자동 백업 30개를 만들고, 변경 없는 확인을 20회 반복한다. 중앙값·p95·전체 내보내기 횟수를 출력하고 테스트 파일은 종료 시 삭제한다. 합성 행은 백업 읽기·해시 비용을 재현하기 위한 것으로 실제 장부 관계와 복원 시간을 검증하는 데이터가 아니다. 정상 테스트 실행에서는 이 실험을 건너뛰고 전용 명령에서만 실행한다. 절대 시간으로 테스트 통과 여부를 판정하지 않는다.

2026-10-11 같은 개발 기기에서 측정한 결과:

| 합성 행 | JSON 크기       | 이전 중앙값 / p95  | 개선 후 중앙값 / p95 | 내보내기 횟수 이전 → 이후 |
| ------- | --------------- | ------------------ | -------------------- | ------------------------- |
| 1,000   | 115,006 bytes   | 17.10 / 17.46 ms   | 0.35 / 0.51 ms       | 20 → 0                    |
| 10,000  | 1,159,006 bytes | 212.22 / 223.02 ms | 0.34 / 0.59 ms       | 20 → 0                    |

재실행·최초 확인, 실제 변경, 강제 백업은 전체 내보내기와 검증을 수행한다. 동일 프로세스의 변경 없는 반복 확인만 빠른 경로를 사용한다. 파일 메타데이터는 계속 확인하며 변경·삭제된 백업은 다시 검증한다. 유효한 백업만 보관 개수와 삭제 대상에 포함한다. SQL total_changes와 data_version을 함께 사용해 같은 연결의 쓰기와 다른 연결의 쓰기를 감지한다. 롤백처럼 내용이 유지된 경우는 기존 내용 해시를 비교하여 중복 저장을 피한다. 키 파일은 장부 백업 대상이 아니다.

파일 내용 검증 결과는 경로·파일 식별자·크기·나노초 수정/변경 시각으로 캐시한다. 파일이 사라지거나 검증에 실패하면 캐시를 비운다. 강제 백업은 DB 변경 유무와 관계없이 새로운 스냅샷을 저장하고, 저장 성공 후 오래된 정상 자동 백업을 정리한다. 최근 30개 보관 정책은 유지한다.

## 다음 측정 범위

- 설치 앱: 실행 요청부터 창 표시와 대시보드 준비까지, 정상 시작과 최초 시작을 구분한다.
- 화면 전환과 조회: 동일 조회 기간·기록 수에서 반복 측정한다.
- API: 네트워크 지연과 로컬 저장 비용을 구분하고 실제 호출 수를 기록한다.
- 메모리: 메인·렌더러·GPU 등 앱 프로세스 전체를 측정하고 반복 전환 후 회수 여부를 확인한다.
- 장부 증가: 1천·1만·10만 건의 관계가 유효한 가짜 장부로 집계와 목록 조회를 검증한다.

자동 백업은 아직 동기 DB/파일 작업을 사용한다. 이번 변경은 반복 읽기와 내보내기 비용을 줄이는 단계다. 최초 검증·변경 시 내보내기·복원은 별도로 측정하고 필요하면 비동기 파일 처리나 작업 스레드로 분리한다. 업데이트 전 백업 완료와 DB 스냅샷 일관성을 먼저 유지한다.

## 보스 통합 API 조회

정산 화면의 통합 확인은 한 IPC 요청으로 주간·월간 기간을 전달한다. 백엔드는 같은 캐릭터 OCID·실제 조회일·기준일의 응답을 요청 안에서만 재사용한다. 현재 주간·월간의 조회일이 같으면 N명에 대한 스케줄러 호출은 2N회에서 N회로 줄어든다. 테스트에서 캐릭터 2명의 주간·월간 기록을 모두 반영하면서 실제 가짜 전송 호출 수가 4회에서 2회로 줄어드는 것을 확인했다. 네트워크 시간의 개선율은 측정하지 않았다.

조회일이 다르면 별도로 호출한다. 재조회는 새 응답을 받으며 응답과 실패 캐시는 통합 요청 이후 유지하지 않는다. 주간·월간 응답 검증과 정산은 독립적이므로 월간 응답만 잘못되거나 해당 기간이 범위 밖이어도 성공한 주간 기록을 유지한다. 두 기간 전체에 일괄 실행 잠금을 적용한다. 조회 중 계정 변경은 기존 IPC 진행 요청 보호를 따른다.

## 페이지 코드 지연 로딩

대시보드는 처음부터 포함하고 나머지 6개 페이지는 React lazy로 해당 메뉴를 처음 열 때 불러온다. 보스 장부 안에서도 기록 편집·드랍·아이콘 관련 코드는 주간·월간 기록을 처음 열 때 불러온다. 업데이트 전용 복구 화면도 별도로 분리하되 복구 진입과 업데이트 확인 동작은 유지한다. 준비 중에는 상태 안내를 표시하며 로딩 오류가 발생해도 메뉴를 유지한다. 페이지 전환은 기존처럼 화면을 새로 마운트하고 DB에서 최신 기록을 읽는다.

빌드 후 npm run perf:bundle로 초기 진입 파일과 정적 의존 파일의 JavaScript 크기를 합산한다. Vite 빌드 매니페스트를 사용하며 동적 import 파일은 초기 크기에서 제외한다. 전체 JavaScript 크기도 함께 출력한다. 오래된 결과를 비교하지 않도록 매번 npm run build 후 실행한다. 압축 전 생성 파일 크기이며 CSS·이미지·Electron 런타임·실행 시간·메모리를 포함하지 않는다.

2026-10-11 비교: 초기 JavaScript 1,020,390 → 695,569 bytes(약 32% 감소). 전체 JavaScript는 분리용 코드와 오류 안내를 포함하여 1,030,608 bytes로 소폭 증가했다. 설치파일이 같은 비율로 작아지는 개선은 아니다. 실제 시작 시간은 별도 설치 앱 프로파일링이 필요하다.

Electron 임시 DB에서 초기 대시보드의 스크립트 파싱 이벤트에 다른 페이지가 포함되지 않는지, 각 페이지를 열면 해당 코드가 실행되는지, 보스 기록은 내부 화면을 열 때 실행되는지 확인했다. 파일 기반 앱에서는 Resource Timing이 지연 로딩 스크립트를 모두 제공하지 않아 Chrome DevTools Protocol의 scriptParsed를 사용했다. 최신 DB 표시가 있는 임시 장부로 업데이트 복구 화면 진입도 검증했다. 사용자 장부와 실제 API는 사용하지 않았다.

## 대량 장부 대시보드 조회

실행: npm run perf:ledger

대시보드는 기간 내 모든 거래의 메모·통화 정보 등을 배열로 읽는 대신, 집계에 필요한 8개 필드만 SQLite iterator로 한 건씩 처리한다. 상세 정보는 먼저 최근 5건을 선택하고 해당 거래만 연결하여 읽는다. 사냥 드랍의 사냥 수입 합산, 수동 수입·지출 구분, 캐릭터별 과거 서버 표시 순서, 일별·월별 빈 구간과 최근 거래 정렬은 유지한다. 금액은 BigInt로 정확히 합산하고 안전한 정수 범위를 넘으면 기존처럼 오류를 안내한다. DB 스키마와 거래 목록·CSV의 전체 조회는 변경하지 않는다.

임시 파일 기반 SQLite에 캐릭터 6명과 관계가 유효한 사냥·수동 수입·수동 지출 1천·1만·10만 건을 생성한다. 외래 키 검사와 집계 결과 일치를 확인한 후, 두 경로를 예열하고 실행 순서를 번갈아 바꾸며 각각 10회 측정한다. 비교 경로는 전체 상세 목록과 요약을 생성한 뒤 같은 집계 함수를 적용한다. 따라서 조회 경로 변경의 비용 차이를 비교하는 실험이며, 이전 배포 앱의 전체 실행 속도를 비교한 결과가 아니다. 데이터 생성과 결과 검증 시간은 측정에 포함하지 않는다. p95는 10개 샘플의 nearest-rank 값이다. 테스트 DB는 종료 시 삭제하며 일반 테스트에서는 벤치마크를 건너뛴다.

2026-10-11 같은 개발 기기의 예열된 조회 결과:

| 기록 수 | 전체 상세 조회 중앙값 / p95 | 개선 경로 중앙값 / p95 | 상세 정보 생성 건수 이전 → 이후 |
| ------- | --------------------------- | ---------------------- | ------------------------------- |
| 1,000   | 5.72 / 6.94 ms              | 3.42 / 4.38 ms         | 1,000 → 5                       |
| 10,000  | 95.02 / 99.71 ms            | 30.70 / 35.38 ms       | 10,000 → 5                      |
| 100,000 | 1,419.04 / 1,462.53 ms      | 628.02 / 660.54 ms     | 100,000 → 5                     |

전체 기록을 하나의 배열로 보관하지 않지만 집계에는 모든 행의 순회가 필요하고 SQLite 정렬도 남아 있다. 앱 전체 메모리, 최초 실행, IPC, 화면 렌더링 시간은 측정하지 않았다. 10만 건에서는 개선 후에도 약 0.6초의 동기 처리가 있으므로 실측에 따라 작업 스레드 분리를 검토한다.

## 거래 목록 페이지 조회

실행: npm run perf:ledger:pages

화면은 전체 거래 목록 대신 집계·수익 묶음과 상세 거래 최대 50건을 받는다. DB에서 먼저 지출·직접 수익만 필터링하고 페이지의 행을 선택한 후 메모·분류·통화 정보 등을 연결한다. 순서와 전체 합계, CSV 내보내기 범위는 기존 기준이다. 페이지 이동 중에는 마지막 조회 조건의 집계만 재사용하며 DB 변경과 필터 변경은 다시 집계한다. 전체 상세 목록이나 여러 조회 조건을 캐시하지 않는다.

대시보드 실험과 같은 관계가 유효한 가짜 장부를 사용한다. 전체 목록과 수익 묶음 계산, 집계 캐시가 없는 첫 페이지, 집계 캐시가 있는 두 번째 페이지를 예열된 SQLite에서 각각 10회 측정한다. 실행 순서를 번갈아 바꾸고 측정 밖에서 전체 합계·수익 묶음·페이지 크기를 검증한다. 첫 페이지는 매회 새 서비스를 만들어 집계 재사용을 막는다. JSON 크기는 실제 IPC에서 사용되는 응답 형태를 직렬화한 UTF-8 byte 수이며, 직렬화·IPC·React 렌더링 시간은 아래 조회 시간에 포함하지 않는다.

2026-10-11 같은 개발 기기의 결과:

| 기록 수 | 전체 조회 중앙값 / p95 | 첫 페이지 중앙값 / p95 | 후속 페이지 중앙값 / p95 | 전체 응답 → 페이지 응답 크기 |
| ------- | ---------------------- | ---------------------- | ------------------------ | ---------------------------- |
| 1,000   | 5.46 / 6.02 ms         | 1.57 / 1.86 ms         | 0.48 / 0.50 ms           | 1,087,765 → 71,434 bytes     |
| 10,000  | 82.48 / 90.96 ms       | 13.13 / 17.34 ms       | 0.83 / 1.13 ms           | 10,882,769 → 71,444 bytes    |
| 100,000 | 1,633.71 / 1,671.33 ms | 596.55 / 649.99 ms     | 21.95 / 22.53 ms         | 108,832,773 → 71,454 bytes   |

가짜 수동 거래에는 긴 한글 메모를 넣었으므로 응답 크기는 일반적인 사용량의 평균을 뜻하지 않는다. 대량 기록의 첫 집계는 여전히 동기 처리이며, 뒤쪽 페이지의 OFFSET 순회와 정렬도 남아 있다. 실제 설치 환경의 최초 조회와 메모리를 측정하여 필요하면 인덱스·작업 스레드·커서 방식 조회를 검토한다. 기존 기록과 백업 형식은 유지한다.
