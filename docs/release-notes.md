# 릴리스 노트 작성

**설정 → 업데이트 내역**에서 앱에 포함된 버전별 변경 사항을 확인한다. 첫 기록은 v0.2.0(2026-10-09)이다. 인터넷 없이 읽을 수 있고, 현재 버전은 배지로 표시한다. 새 버전으로 업데이트하면 그 버전까지의 기록이 함께 들어온다. 설치 전 새 버전의 내역은 GitHub Releases에서 확인한다.

원본은 `src/shared/release-notes.json` 하나다. 앱은 이 파일을 표시하고, 배포 스크립트는 같은 파일에서 해당 버전의 Markdown을 만들어 GitHub 릴리스 본문에 사용한다. 이미 공개한 기록은 보존하며 다음 배포를 준비할 때 새 항목을 맨 위에 추가한다.

v0.2.1은 개발 장부의 기존 기록 유지 수정까지 포함하여 확정했다. 이후 개발 버전은 v0.2.2이며 새 기능·수정은 v0.2.2 내역에 작성한다. v0.2.2의 첫 기능은 화면 테마 선택이며 해당 내역을 새 항목에 기록했다. 추가 개발은 같은 항목에 기능별로 기록하고 실제 배포 시 날짜를 확정한다. 확정된 내역은 `node scripts/release-notes.mjs 0.2.1`로 확인한다.

```json
{
  "version": "0.2.1",
  "date": "2026-10-09",
  "title": "캐릭터·주간 콘텐츠와 장부 개선",
  "summary": "캐릭터 정보와 주간 콘텐츠, 장부 관리를 개선했습니다.",
  "sections": [
    {
      "title": "캐릭터 관리",
      "changes": ["캐릭터 외형 이미지와 오른쪽 프로필 정보를 제공합니다."]
    },
    {
      "title": "주간 콘텐츠",
      "changes": ["이번 주와 지난주 조회 결과를 확인할 수 있습니다."]
    }
  ]
}
```

예시의 버전과 날짜는 실제 배포에 맞춘다. `sections`에 기능별 제목과 변경 목록을 작성한다. 앱에서는 소제목으로, GitHub 릴리스에서는 Markdown 제목으로 표시한다. 한 기능의 관련 변경을 함께 묶고 사용자 입장에서 달라진 동작을 한 줄씩 작성한다. 기능 제목은 중복 없이 작성한다. 기존 버전의 단순 `changes` 목록도 지원하지만 한 버전에 두 형식을 동시에 사용하지 않는다. 가장 새 버전부터 배열에 넣으며 버전·날짜·제목·설명·변경 사항은 비워두지 않는다.

```bash
# 현재 package.json 버전의 노트 미리 보기
npm run release:notes

# 원하는 버전의 노트 미리 보기
node scripts/release-notes.mjs 0.2.0
```

스크립트가 날짜·버전·순서·필수 내용을 검사하며 해당 버전의 노트가 없으면 실패한다. GitHub Actions에서도 같은 검사를 실행하고 성공해야 공개할 수 있다. 기존 v0.2.0 태그를 다시 올리지 않는다. 이번 화면 변경은 다음 버전 배포에 포함한다.

## 브랜치와 배포 시점

현재 배포는 *_커밋이나 main 푸시가 아니라 v_ 태그 푸시**로 시작한다. main에 여러 기능을 차례로 커밋해도 매번 업데이트가 제공되지 않는다. 혼자 개발하는 동안 main 하나로 작업하고, 완성된 기능들을 묶어 버전·노트를 정리한 뒤 태그를 올리는 방식으로 충분하다.

작업 중인 변경을 안정된 main과 분리하고 싶다면 기능별 브랜치를 쓴다. 예를 들어 `codex/release-notes`에서 수정·검증하고 완료 후 main에 병합한다. main에서 버전과 노트를 확정하고 태그를 올린다. 지금은 별도의 develop 브랜치를 운영할 필요는 없다. 브랜치를 사용해도 배포 여부는 태그로 결정한다.

배포 순서: 기능 구현·검증 → 버전 갱신 → 노트 작성 → 커밋·main 반영 → 배포 태그 푸시 → GitHub Actions와 Releases 확인. 명령은 [앱 업데이트](app-updates.md)를 참고한다.
